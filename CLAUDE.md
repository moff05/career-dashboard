# Career Dashboard — CLAUDE.md

Multi-user, self-hostable job tracker with two AI features bolted on deliberately: per-job fit scoring, and a coach that knows your background. Next.js 16 (App Router), TypeScript, Tailwind CSS, Turso (libsql) for storage, Groq (OpenAI-compatible SDK, `lib/groq.ts`) for AI. No accounts or passwords — each visitor gets a client-generated UUID identity. AI runs server-side on a shared `GROQ_API_KEY`; users do not supply their own AI key. Live at `career-dashboard-ten.vercel.app`, repo `github.com/moff05/career-dashboard`.

Originally built as a single-user tool for Nicholas Moffett (University of Miami junior, CRE/AI intern) — his is still the reference persona for feature priorities and tone, but as of the multi-user launch (June 2026) the app no longer hardcodes his data. Anyone using the live instance or a self-hosted copy gets their own isolated profile, jobs, memories, and chat history.

**Product philosophy (post-reshape, June 2026):** this is meant to feel like a great spreadsheet job tracker, not an AI platform. AI earns its place only where it removes real friction — parsing a job posting, scoring fit, knowing your background in chat — not as a feature-count exercise. See "Cut" in the roadmap below for what got removed and why; if a new feature idea reads as "AI restates something already visible elsewhere," that's a signal to cut, not build.

## Multi-user model

- First visit with no `cid_user_id` in `localStorage` → `ClientRoot` (`app/ClientRoot.tsx`) redirects to `/welcome`.
- `/welcome` (`app/welcome/page.tsx`) offers two paths: **Get Started** → `/setup`'s 3-step onboarding flow (**resume** → **identity** → **background**), or **"Already have a backup? Restore it instead"** — an inline panel (backup `.json` file) that skips the form entirely: generates a UUID, `POST`s straight to `/api/import` under that new id, and only persists the identity to `localStorage` once the import actually succeeds. This is the only way to reach a restore on a fresh browser/device — without it, `/api/import`'s target user_id doesn't exist until `/setup` creates one, and the "Restore from backup" button on Profile is unreachable pre-setup.
- On finish (either path): client generates a UUID (`crypto.randomUUID()`), saves `cid_user_id` / `cid_display_name` to `localStorage`, then `PUT`s the profile (and resume, if provided) or `POST`s the imported backup to the API with those values as headers.
- Every later request goes through `lib/apiFetch.ts`, which auto-injects the `x-user-id` header from `localStorage`.
- Server-side, `lib/user.ts`'s `getUserId` reads `x-user-id` from every request. A missing `x-user-id` gets a fresh `randomUUID()` per request rather than the old shared `'anonymous'` bucket, so two different header-less callers can no longer read or overwrite each other's data. Every route that takes an `[id]` param scopes both the write *and* any response lookup by `user_id` — a guessed/enumerated id should 404, never leak another user's record (see the IDOR fix in the roadmap).
- AI calls use the server-side `GROQ_API_KEY` env var only — no per-user key required. `isSystemUser()` gates AI routes to reject synthetic/health-check user IDs (those starting with `__`).

## Database

`lib/db.ts` → `getDb()` returns a singleton `@libsql/client`, pointed at `TURSO_DATABASE_URL`/`TURSO_AUTH_TOKEN` in production or a local SQLite file (`file:./data/career.db`) when those env vars are absent.

Schema lives in `scripts/migrate-multi-user.ts` — `npm run migrate` creates all tables (if missing) and adds `user_id` columns + indexes (safe to re-run). The legacy single-user migrations (`migrate.ts`, `migrate-v2.ts`, `migrate-v3.ts`) have been deleted — this is the only migration script now.

**Active tables (all scoped by `user_id` unless noted):**
- `profile` — name, email, phone, linkedin, university, degree, graduation_date, gpa, honors, minors, target_roles, target_cities, work_authorization, notes, resume_text. Unique per `user_id`.
- `jobs` — company, title, type, status, match_score, posting_date, deadline, url, description, salary_range, location, source, notes, starred, status_updated_at. `url` is nullable — a job can be pasted-text-only with no link.
- `chat_messages` — role, content, session_id (UUID per browser session). Coach chat only.
- `memories` — AI-extracted facts from Coach conversations. Categories: preference, goal, insight, company, role, location, skill, other, story_bank.
- `resume` — name, raw_text, parsed_at, is_default. Multiple resumes per `user_id` are allowed; a partial unique index (`idx_resume_one_default`) enforces at most one `is_default = 1` row per user. AI features always read whichever resume is currently default.
- `connections` — company, name, email, role, linkedin, relationship, notes, status, `company_id` (FK to `companies`). Status cycle is `not_reached_out` → `reached_out` → `responded` → `talked` → `warm` (`talked` added 2026-08-26, between `responded` and `warm`) — `CONN_STATUS`/`CONN_CYCLE` in `ConnectionsPanel.tsx`. `company` is free text, not required to match a tracked job.
- `connection_notes` — a running, dated log of interactions per connection (entry_date, note), separate from `connections.notes` (a single freeform field a new entry would otherwise overwrite). Added/viewed via `ConnectionLog.tsx`, `GET/POST /api/connections/[id]/notes`. The Priorities strip's connection follow-up reminders (see below) read the most recent entry per connection.
- `companies` — name, status, notes, `career_url` (added via `addColumn`, resolved to an ATS board by `resolveBoard()` for the job-board scan — see below). A lightweight pre-application target list, decoupled from tracked jobs the same way `connections` is.
- `usage_log` — one row per AI call: route, model, input/output/cache tokens, web_search_requests, cost_usd. Written by `lib/usage.ts`, read by the Profile page's Usage & Cost card.
- `discovered_jobs` — pending review queue from the board-scan (see "Job-board scan" below): company, title, type, location, url, description, posting_date, source, match_score, score_data, status (`pending` / `added` / `dismissed` / `discarded`), `career_url` (nullable — only set on a row the expanded search staged, see below), created_at. `(user_id, url)` is a unique index — doubles as the dedup record so a posting is never re-surfaced once seen, even after it's been dismissed or discarded.
- `gemini_grounding_calls` — one row per Google Search-grounded Gemini call made by the expanded board-search (see below), timestamped only (`called_at`) — a global counter (not scoped by `user_id`, since Google's free quota is per-project, not per-app-user) enforcing `MONTHLY_GROUNDING_CAP` in `lib/discoverCompanies.ts`.

**Legacy/orphaned tables** (still created by the migration for backward compatibility with old data, no longer written by any current feature): `timeline_events`, `leads`, `company_ats_cache` — these backed the cut Timeline, Discover/Hunt Agent, and Discover/leads-liveness features. Not deleted on purpose (no destructive `DROP TABLE` without being asked); if you're touching this schema, don't build new features against them without checking they're really meant to come back.

There is no hardcoded seed data anymore — a fresh `user_id` starts with empty tables until they complete `/setup` and start using the app.

Coach, Profile/Memory, and Connections are summonable panels rendered globally from `layout.tsx`, opened via `useOverlays()` (`app/OverlayContext.tsx`), not routes. There is no sidebar and no per-page nav; the header (`app/layout.tsx`) is a slim, sticky top bar with the `jobs_` wordmark on the left (no icon mark — tried a fox-head logo, cut it, see roadmap) and Connections/Coach/Profile triggers on the right.

## Core workflow

**Import a job → get an AI fit score → track it.** `/api/jobs/import` accepts a URL, pasted job description text, or both (a URL alone fetches and parses the page; pasted text alone works with no link at all — this was deliberately relaxed so a JD without a link doesn't need Coach as a workaround). No data is seeded — every job entry comes from a real link, pasted text, or manual entry.

## AI context (system prompt)

`buildSystemPrompt(userId)` in `lib/ai-context.ts` builds every AI call's system prompt, all scoped to that `user_id`:
- Resume text (or `'Resume not yet added.'` if none saved)
- Profile fields: name, graduation date, target roles, target cities, notes
- Memories grouped by category, each tagged with its save date
- Job tracker summary, grouped by status
- Today's date (dynamic)
- An explicit instruction that memories are notes from past conversations, not fixed truth — the model is told to trust a more recent memory or whatever the user is currently saying over an older stored fact, rather than holding someone to a stale stated goal

An unconfigured user (hasn't completed `/setup`) gets a generic prompt with placeholders — there's no hardcoded personal data anywhere in this path anymore.

## Memory system

After each Coach chat response, `/api/chat/memories` is called with the user message + AI response. A lightweight Haiku call extracts new facts about that user and saves them to their `memories` rows. The Coach page shows a toast when a memory is saved. Memories are dated when shown back to the model (see AI context above) so recency can outweigh an older, possibly-stale fact — this was a deliberate fix for the failure mode where the model over-anchors on old memory and resists a user's stated change of plans.

## Company badges

Companies display vibrant hash-based initials badges — no network calls, no Clearbit dependency. Color is deterministic per company name using a 12-color palette. `CompanyBadge` is defined locally in `app/page.tsx`. These categorical company/status/score colors are a deliberate exception to the monochrome system (see Design system) — they exist to disambiguate at a glance, not to decorate.

## The main page (`app/page.tsx`)

Greeting + Priorities strip, then two tabs — **Tracker** (stats + the job tracker table) and **Discovered** (the board-scan review queue, with a count badge when non-empty) — top to bottom, one page:
- **Greeting + Priorities** — `getPriorities(jobs)` computes free, no-AI-call priority items from whatever's already loaded: deadlines (≤3 days = urgent, ≤7 = soon), 14+ day no-response follow-ups, interview-prep flags. `getConnectionFollowups(connections)` (`app/lib/jobUtils.tsx`, added 2026-09-28) adds the same staleness pattern to connections — 14+ days since the last `connection_notes` entry surfaces a "Reach out" item, ranked ahead of job follow-ups since a deliberately-logged personal action is more actionable than a passive no-response wait; a connection with zero log entries never appears here (nothing to go stale). Sorted by urgency bucket first (deadline > connection follow-up > job follow-up > interview prep), then `match_score` descending as a tiebreaker within a bucket; top 5 shown (bumped from 3 once connection follow-ups made 3 too easy to overflow). Clicking a job-rooted item calls `jumpToJob(id)` — expands that job's row below and scrolls to it. A connection follow-up instead opens the Connections overlay pre-searched to that name (`openConnections(undefined, name)` — see OverlayContext's `connectionsFocusQuery`). An "interview prep" priority opens the Coach overlay with a prefilled prompt about that job. This is the only "what should I prioritize" surface — Weekly Brief and the Strategy advisor were both cut as redundant with it (see roadmap). Sits above both tabs — visible regardless of which one is active.
- **Add a Job (primary)** — one button, one modal, two paths: paste a URL/description for AI auto-fill (review/edit → save), or click "skip straight to typing it in yourself" to jump to the same blank form. A URL alone fetches and parses the page (Jina reader first, falls back to plain fetch); pasted text alone needs no link. Combines up to 4 context sources (URL, pasted text, screenshot, extra link) before extracting structured fields in one Haiku pass. Fields not found anywhere are left blank — no data is invented. No API key → a friendly inline prompt to add one in Profile instead of attempting the call.
- **Source detection** — URL hostname mapped to a source label (LinkedIn, Greenhouse, Lever, Workday, Handshake, etc.); pasted-text-only jobs are labeled "Pasted."
- **Flat, sortable job list** (Sept 2026 — see roadmap) — no company-group accordion anymore. Each row shows its company inline (a kicker line above the title); click a row to expand its own detail panel. The two-level accordion (company group → job row) was cut because most tracked companies only have 1-2 roles, so the extra grouping level was friction without payoff. Sortable by Company, Title, Type, Status, Score, Deadline, Posted (click a column header, 3-click cycle: asc → desc → off). Default (no explicit sort): starred jobs float to the top, then most-recently-added.
- **Job type** condensed to `full-time` / `part-time` / `internship` (`TYPE_OPTIONS` in `app/lib/jobUtils.tsx`) — the old fall/spring/summer-internship season split (plus a `type_year` field) was cut as unnecessary once someone is only tracking full-time roles; the `type_year` DB column still exists but nothing writes to it anymore.
- **Inline status change** — click status badge → dropdown → `PATCH` partial update.
- **Detail slide panel** — location, deadline countdown, source, salary, URL, notes, a collapsible full-description block, plus AI Score / Cover Letter / Fit Gaps / Bullets tabs. These are the only per-job AI surfaces — there is no "discuss with Coach" handoff anymore (cut deliberately; Coach is general-only, see below). The Overview tab's Network section lists connections at that job's company (view/status-cycle/delete in context) but adding/editing one always opens the standalone Connections overlay — see Networking / connections below.
- **Search + filter, column sorting, smart deadline countdown.**
- **Empty state** — tracker starts empty; prompts the user to import a job.

## Job-board scan (Discovered tab)

For any user with `target_roles` and `target_cities` set in Profile, a **weekly** cron (`vercel.json`, Mondays 13:00 UTC → `GET /api/cron/scan-boards`) scans that user's own tracked Companies list — whichever resolve to a Greenhouse/Lever/Ashby/Workday board via `companies.career_url` (`lib/boardCompanies.ts`) — filters postings by role/city match, scores survivors with the same fit rubric as a manual AI Score (`lib/scoreJobFit.ts`), and stages up to `TOP_N` (20) as `pending` rows in `discovered_jobs`. Nothing ever touches the real `jobs` table automatically — the user reviews each one from the Discovered tab and explicitly Adds or Dismisses it (`PATCH /api/discovered/[id]`).

The per-user scan/filter/score/stage logic lives in `lib/scanBoards.ts` (`scanBoardsForUser`), shared by two callers:
- The cron route loops every eligible user, sharing one `postingsCache` across them so two users tracking the same company don't double-fetch its board.
- **Manual refresh** (`POST /api/discovered/refresh`) lets a user pull a fresh batch without waiting for next Monday — but only once their current queue is fully cleared (zero `pending` rows). This is deliberate: approving or dismissing everything in the current batch is the signal that they've actually looked at it, which is what unlocks pulling the next one. Refreshing while unreviewed rows still exist would just bury them under a second batch, so the route 409s instead. The Discovered tab's Refresh button is disabled for the same reason whenever `discoveredJobs.length > 0`.

Each Discovered row expands (click anywhere on the row, not just the chevron) to show the same score-category breakdown as a tracked job's AI Score tab (summary + per-category bars, read from `d.score_data` — already computed at scan time, no extra AI call) plus the full parsed description in a collapsible block. `GET /api/discovered` also returns `lastScanAt` (`MAX(created_at)` across any status for that user) so the tab can show "Last scanned Xh/d ago."

**Safety history — read before touching the matching logic in `lib/scanBoards.ts` or the cron route.** An earlier version matched on single words extracted from `target_roles` ("engineer", "data", "analyst", ...) and inserted directly into the real tracker. Tested once against production, it matched almost every posting on a few large boards and wrote 1,030 junk rows into two real users' trackers before being caught and cleaned up. Two fixes came out of that and must not regress: (1) matching requires a bigram or exact phrase from `target_roles` — a single generic word is never enough; (2) nothing touches the real `jobs` table until the user explicitly approves a specific posting via the staging table. Use `?dryRun=1` on the cron route and/or a local sqlite DB to test any further change to the matching logic, not production.

**Malformed-posting crash (2026-09-28, commit 7ac7fe7).** JLL's Workday board occasionally lists a posting mid-transition with only `bulletFields` set — no `title`, `location`, or `externalPath` at all. `matchesKeywords(posting.title, ...)` crashed on the `undefined` title, 500ing every manual refresh and the weekly cron alike for any user tracking a company on that board (confirmed by paginating JLL's real Workday API directly and finding the exact record before writing the fix). `fetchWorkday()` in `lib/boardCompanies.ts` now skips any posting missing `title`/`externalPath` rather than trusting the platform's shape. If Discovered ever silently stops updating again (`lastScanAt` stuck, refresh 500ing), check for this same failure mode on any tracked company's board before assuming something else broke.

**Expanded company search (2026-09-28, commit c98e349 — built and gated, not yet live).** When a user's own tracked Companies stage fewer than `EXPAND_THRESHOLD` (5) matches in a run, `findSimilarCompanies()` (`lib/discoverCompanies.ts`) asks Gemini — with Google Search grounding — for other real companies in a similar space. This is the one place in the feature that can suggest a company the user never chose to track, so nothing from it is trusted at face value: every suggestion still has to independently `resolveBoard()` **and** successfully fetch real postings before anything is staged; a hallucinated name or a URL that looks right but isn't live is dropped silently, never surfaced. Approving a discovered job whose company isn't tracked yet seeds that company's `career_url` (`findOrCreateCompany`'s new optional third param) so future scans check it directly instead of only ever resurfacing through another expanded search.
- **Requires `GEMINI_API_KEY`** — quietly a no-op without it (`findSimilarCompanies` returns `[]` immediately). **Not currently set on Vercel** — this whole path is inert in production right now.
- **Hard-blocked as of 2026-09-28**: Google Search grounding needs a billing account linked to the Gemini project to work *at all* (confirmed live — every grounded call 429s on a brand-new key even before any quota is used). Billing was linked and the key still 429'd after 8+ minutes of polling, matching a documented Google-side bug (project stuck showing "Free tier" despite a confirmed paid-tier upgrade — see Google's own dev forum, e.g. `discuss.ai.google.dev/t/gemini-api-stuck-on-free-tier-429-despite-confirmed-tier-1-prepay-billing`). Paused pending that clearing on Google's end — before resuming, retest with a plain `generateContent` call (no tools) to confirm the key works at all, then the same call with `tools: [{googleSearch: {}}]` to check grounding specifically.
- **Hard monthly cap**: `MONTHLY_GROUNDING_CAP = 500` in `lib/discoverCompanies.ts`, tracked via the `gemini_grounding_calls` table — well under Google's free 5,000/month (shared across Gemini 3.x models), purely so a bug/retry loop can't quietly run past the free tier and start charging the real card now on the account.
- **Model pin**: `gemini-3.8-flash` — `gemini-2.5-flash` (this app's first pick) was already 404ing as "no longer available to new users" by the time this shipped. Check `GET /v1beta/models` with the live key if this 404s again.

## Networking / connections (overlay, `app/components/ConnectionsPanel.tsx`)

- **Decoupled from tracked jobs.** A connection is `{company, name, email, role, linkedin, relationship, notes, status}` — `company` is free text, never required to match a job you've actually tracked. You can log a recruiter you met at a career fair from a company you have no job tracked at yet; that was the whole point of pulling this out of the per-job panel. `GET /api/connections` (no `company` param) lists everything for the standalone overlay; passing `?company=X` filters, which is what the in-job Network view still uses.
- Outreach status cycles `not_reached_out` → `reached_out` → `responded` → `talked` → `warm` (`CONN_STATUS`/`CONN_CYCLE`, exported from `ConnectionsPanel.tsx`). A separate dated conversation log (`connection_notes` table, `ConnectionLog.tsx`, "+ Log an update"/"View log") tracks individual interactions over time — distinct from the single `notes` field, which a new update would otherwise overwrite.
- One add/edit form in the whole app, inside the overlay — the old per-job inline add-form (name/relationship/notes only, no email/role/linkedin) was removed in favor of this. Opening the overlay from a job's Network tab (`openConnections(job.company)`) pre-fills the company field.
- Company-keyed for display — contacts at a company show up across every job tracked at that company, and in the standalone overlay grouped the same way.
- `app/api/connections/route.ts` (`GET`/`POST`), `connections/[id]/route.ts` (`PATCH` — general partial update across any editable field, not status-only; `DELETE`).

## API notes

- `PUT /api/jobs/[id]` — full update, requires all fields. `PATCH` — partial update (e.g. status only). Both scope the response lookup by `user_id`, not just the write — see Multi-user model.
- `POST /api/jobs/import` — `{ url?, extraText?, imageBase64?, imageMediaType?, extraLink? }`, requires at least one of `url`/`extraText` → Haiku extraction, returns `{ company, title, location, type, deadline, salary_range, description, url, source, warning? }`. `url` in the response is `null` when none was given.
- `POST /api/jobs/[id]/analyze` — 5-category fit scorecard, each category constrained to an enum of anchored values, weighted to a total out of 100: Explicit Requirements Met (0-25), Skills Match (0-25), Role Alignment (0-25), Industry Fit (0-10), Logistics/Location Fit (0-15). Industry Fit was cut from 20→10 (2026-09-02) — at 20% weight with zero credit for transferable skills, it was structurally close to unwinnable for an early-career candidate applying across industries; the freed 10 points went to Skills Match and Role Alignment instead. The Explicit Requirements rubric also explicitly credits any one satisfied path in an "X, Y, or Z" alternative-qualifying-paths requirement rather than only the first-listed one. `openai/gpt-oss-120b` (`ANALYZE_MODEL` in `lib/scoreJobFit.ts`, aliased to the same `GEMINI_MODEL` every other route uses — see AI model usage below for why), `temperature: 0`. A truncated response (this model can burn most of its completion budget on hidden reasoning before writing JSON) is detected server-side (missing category rationale/summary, checked against `finish_reason`) and errored rather than silently defaulting a cut-off category to a score of 0. Scores *fit for this specific posting*, not general candidate strength — scored against what's literally on the resume today, with explicit-requirement misses capped low regardless of overall strength. Color coding on the total: 80+ green, 60–79 amber, <60 red; per-category bars are colored by percent-of-that-category's-max, not the raw score. This is the per-job AI score the whole tracker is built around.
- `POST /api/jobs/[id]/gaps`, `POST /api/jobs/[id]/bullets`, `POST /api/jobs/[id]/cover-letter` — per-job AI panels, all read from `buildSystemPrompt(userId)` + the job record.
- `GET /api/export` — full data dump for the current user across all active tables. `POST /api/import` — restores from that dump into the current user (upserts profile, appends everything else including resumes). Used by Profile's Backup & Restore card, and by `/welcome`'s restore shortcut for a fresh browser/device; the only recovery path since there are no accounts.
- `GET /api/resumes` — list the user's resumes (default first). `POST /api/resumes` — create one (`{name, raw_text}`); the first resume for a user is auto-marked default. `PUT /api/resumes/[id]` — update `name`/`raw_text`, or pass `{set_default: true}` to make it the one AI features read (clears the previous default first to respect the partial unique index). `DELETE /api/resumes/[id]` — deletes it; if it was the default, the oldest remaining resume is auto-promoted.

## AI model usage

All AI calls go through Groq via the OpenAI-compatible client in `lib/groq.ts`, using the server-side `GROQ_API_KEY`. One model now for everything, `GEMINI_MODEL = openai/gpt-oss-120b` (generative routes — coach chat, memory extraction, fit gaps, resume bullets, cover letter, job import parsing — and the fit scorecard alike). This wasn't always the case: `qwen/qwen3.6-27b` was originally the dedicated fit-scorecard reasoning model, but Groq started output-rate-limiting it below what a 5-category rubric response actually needs, so the analyze route was switched onto the same model as everything else (`ANALYZE_MODEL = GEMINI_MODEL` in `lib/scoreJobFit.ts` — a plain alias, not a separate constant, specifically so the two can't silently drift apart again). `temperature: 0`, structured JSON output so each rubric sub-score can only land on one of its anchored values — see API notes above. Every call goes through `createChatCompletion()`/`createChatCompletionStream()` in `lib/groq.ts`, which retries up to 3x on a 429 using Groq's own `retry-after` header, honoring a caller-supplied `deadlineAtMs` (the board scan passes its own shared deadline so retries across several scored candidates in one invocation can't blow the real remaining time — see Done #42), an explicit per-attempt request timeout (capped 20s, shrinking as the deadline nears, so a merely-slow-not-erroring call can't hang the whole thing either), and `maxRetries: 0` on the underlying SDK call (its own default internal retry was silently stacking with this wrapper's — see Done #42's 3rd fix). Read that file's comments in full before touching retry/timeout behavior; each layer was added to fix a real, live failure the previous layer didn't cover.

**TPM ceiling — this account's real constraint, not fully solved by retries.** Groq's 8,000-tokens-per-minute cap is shared across every route and every user of this app, and a single fit-scorecard call alone requests 5,000–6,000+ tokens — meaning at most ~1 large call can reliably succeed per rolling minute even with zero contention from other traffic. All the retry/timeout logic above makes failures *clean* (a candidate that can't be scored this run is skipped, not a hung function) but doesn't raise the ceiling itself. As real external usage grows, expect more candidates to get skipped per board-scan run for this reason — Groq's own error message points to "Dev Tier" as the actual fix once this recurs often enough to matter (see "Not yet done").

**Model-pin risk, twice bitten:** Groq has removed a pinned model out from under this app before (`llama-3.3-70b-versatile`, 2026-08-21) — if a route starts 404ing with `model_not_found`, check `GET https://api.groq.com/openai/v1/models` with the live key for the current lineup before assuming anything else is wrong.

Root-caused with temporary timing debug logs rather than guessing, in three layers, each confirmed live before moving to the next:
    1. `withGroqRetry` (`lib/groq.ts`) budgeted every call as a fresh `MAX_DURATION_MS` from that call's own start — harmless for `analyze` (one call per invocation) but wrong for the board scan, which scores several candidates in one invocation: a candidate scored late in the loop could "budget" itself a fresh ~55s of retries with only seconds of real platform time left. Fixed by threading the scan's own `startedAt + TIME_BUDGET_MS` through as an explicit `deadlineAtMs` (`scoreJobFit`'s new optional 3rd param) so every retry across the whole request respects one real deadline.
    2. That alone didn't fix it — the failure logged zero errors even after the fix, meaning some calls were just silently *slow*, not erroring. Added an explicit per-attempt request timeout (openai SDK's `{timeout}` option, capped at 20s and shrunk further as the deadline approaches) so a hung call fails fast instead of eating the whole budget unnoticed.
    3. Still not enough — debug logs showed one candidate taking ~20.7s despite the 20s cap. Root cause: the OpenAI SDK's own default `maxRetries: 2` (meant for generic 5xx/network errors) was silently retrying a 429 *internally*, before it ever reached `withGroqRetry`'s own catch block — two independent retry layers stacking with no shared awareness of the real deadline or Groq's `retry-after` header. Fixed with `maxRetries: 0` on every call, since `withGroqRetry` already handles 429s correctly on its own.
    - **Verified fully live afterward**: re-triggered the same real account's scan — 2 of 4 real candidates scored and staged cleanly (`{"ok":true,"staged":2,"scored":2}`), the other 2 failed on genuine Groq TPM exhaustion (`Used 7647/8000`) and were skipped cleanly instead of hanging the function. This is the intended degraded-but-working behavior, not a remaining bug — see the "TPM ceiling" note under AI model usage for why some contention is unavoidable at current account tier.
    - **How to apply**: this bug affected *any* run scoring 2+ candidates in one invocation — the weekly cron (all users, one shared invocation loop) was equally exposed, not just manual refresh. If Discovered still looks stuck for a real user after this fix, re-check with the same debug-logging approach (bracket board-fetch/dedup/each-candidate-scoring with timestamped `console.error` lines) rather than assuming the cause is the same as before.
